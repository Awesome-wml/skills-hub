# Git Batch Commit Zh

## 概述

这个 skill 约束 Codex 在当前仓库里的 Git 协作行为。

- 用户说“分批提交”时，按内容分批提交，不把不相关改动混进同一个 commit
- 用户说“推送”时，直接 push 当前分支
- 所有由该 skill 生成的 commit message 一律使用中文

## 触发词与对应动作

### 1. 用户说“分批提交”

立即进入 Git 提交流程，不先停在口头建议。

### 2. 用户说“推送”

直接执行 push 当前分支，不额外追问是否推送，除非遇到真实阻塞，例如无上游分支、认证失败或远端拒绝。

## “分批提交”执行规则

### 1. 先看清工作区

先执行只读检查，至少包括：

- `git status --short`
- 必要时查看 `git diff --stat`、`git diff`、`git diff --cached`

目标是先弄清：

- 有哪些改动
- 哪些改动属于同一功能或同一类修复
- 是否存在明显噪音文件，例如 `.DS_Store`
- 是否存在用户之前留下但与本次任务无关的改动

### 2. 按内容拆分 commit

分批的标准是“语义原子化”，优先按下面方式拆：

- 不同业务功能分开提交
- 代码逻辑改动与纯文档改动分开提交
- 新增接口封装与页面接入可分开时，尽量分开
- 重构、修复、样式调整、配置修改能独立时，不要混在一起
- 如果多个文件共同组成一个不可拆的功能闭环，可以放进同一批

如果同一个文件里混有多类变更，优先使用分块暂存能力做更细粒度拆分；如果拆分会显著增加风险，则选择更安全的最小可行分组，并在最终说明里明确。

### 3. 提交前检查

每一批提交前都要确认暂存区内容与本批意图一致。至少执行：

- `git diff --cached --stat`
- 必要时查看 `git diff --cached`

不要把明显无关的文件一并提交。尤其注意：

- 用户未要求的 `.DS_Store`
- 纯本地缓存文件
- 与当前任务无关、且不是这次要求一起提交的历史脏改动

### 4. commit message 规则

commit message 必须使用中文，要求：

- 简洁明确，优先使用“动词 + 对象/模块”的写法
- 直接描述这一批改动的核心内容
- 避免空泛表述，例如“更新一下”“修改内容”

推荐风格示例：

- `新增拣货任务接口封装`
- `完善收货单列表筛选交互`
- `调整工作台仓储入口配置`
- `补充 WMS 入库联调方案文档`

### 5. 执行方式

按批次重复执行：

1. 选择本批文件或 hunks
2. `git add ...`
3. 校验暂存区内容
4. `git commit -m "中文 message"`

如果存在多批改动，持续提交直到目标范围内的改动都已完成提交。

### 6. 最终反馈

完成后简要告知用户：

- 一共提交了几批
- 每批 commit message 是什么
- 是否还有未提交改动

## “推送”执行规则

### 1. 默认行为

用户说“推送”时，直接推送当前分支。

优先检查：

- 当前分支名
- 是否已存在上游分支

然后执行合适的 push。

### 2. 异常处理

只有在这些情况才需要向用户说明阻塞：

- 当前不在可推送分支
- 远端认证失败
- 远端拒绝推送
- 需要用户批准提权或网络权限

除真实阻塞外，不要在“推送”前再次确认。

## 注意事项

- 不要改写用户已有 commit 历史，除非用户明确要求
- 不要使用破坏性 Git 命令，例如 `git reset --hard`
- 工作区存在他人或用户的无关改动时，不要擅自清理
- 分批提交的目标是让历史可读、可回滚、可审阅，不是机械按文件数量拆分
