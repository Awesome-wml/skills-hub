# PRD 转可执行技术方案

对照项目架构知识库和现有代码，将 PRD 文档转化为**可执行的技术实现文档**。

核心原则：
- **架构优先**：技术方案必须符合当前系统架构设计，不引入架构违规
- **冲突必答**：当 PRD 与架构冲突时，不只标记问题，还要给出符合架构的替代方案
- **可执行**：输出的技术文档应具体到表结构、接口定义、代码路径，开发人员可直接照做

---

## 1. 输入确认

开始前确认以下信息（缺哪个问哪个，不逐条追问）：

| 信息 | 来源 | 默认值 |
|------|------|--------|
| PRD 文档 | 用户提供（本地路径 / 飞书 wiki 链接 / 禅道需求） | 无，必须提供 |
| 代码基线 | 远端主干 | `origin/dev`（不是当前工作区签出的分支） |
| 架构知识库 | template-scaffold/docs/ | `$OCTOPUS_ROOT/template-scaffold/docs/` |
| 后端代码 | octopus-cloud | `$OCTOPUS_ROOT/octopus-cloud/` |
| 前端代码 | octopus-admin | `$OCTOPUS_ROOT/octopus-admin/` |
| 模块级文档 | octopus-cloud/doc/ 下对应模块 | 自动扫描 |

## 2. 工作流

### Step 0 — 确认基线与 PRD 是否已定稿

- **代码基线用 `origin/dev`**：工作区常签出在落后的功能分支，直接读工作区会把已改掉的旧代码当现状。先 `git fetch origin dev`，再确认要引用的文件在工作区与 `origin/dev` 无差异（`git diff origin/dev -- <path>`），有差异就以 `git show origin/dev:<path>` 为准；产出文档的「概要」里写明基线（分支 + commit + 日期）。
- **PRD 还在改就先等**：用户表示 PRD / spec 正在修改时，等新稿落定再出方案，不按「旧稿 + 对话口头决策」拼凑；新稿与现有实现有差异时先列出差异再写方案。

### Step 1 — 读取 PRD

1. 读取用户指定的 PRD 文档。给的是链接时先取原文，不凭标题推断：飞书 wiki 用 `lark-cli ... --as bot` 读 `raw_content`，禅道图片用 `api.php/v1/files/<fileID>`，CoDesign 原型用本机 Chrome headless 截图（读法见 `prd` 技能「第一步：读取需求源」，只读方式见 `wiki-read-only` 技能）
2. 提取关键信息：
   - 涉及的业务域（商品、订单、门店、仓库、供应商、结算、履约、分销、营销等）
   - 涉及的实体/表（从字段描述中推断）
   - 涉及的角色与权限
   - 涉及的状态流转
   - 涉及的接口/页面

### Step 2 — 加载相关架构知识库

根据 PRD 涉及的业务域，有选择地加载 `template-scaffold/docs/` 下的相关文档：

| 业务域 | 必读文档 |
|--------|---------|
| 通用（所有 PRD） | `database-boundary-baseline.md`, `identity-governance-baseline.md`, `how-to-use.md` |
| 组织/商家/门店/供应商 | `org-model-guide.md`, `agreement-architecture.md`, `org-cooperation-convergence-checklist.md` |
| 商品 | `product-model-guide.md`, `channel-product-design.md` |
| 订单 | `order-model-guide.md`, `order-contract-plan.md` |
| 履约/仓库/配送 | `fulfillment-model-guide.md`, `fulfillment-gap-analysis.md` |
| 分销/合作/BD | `distribution-design.md`, `agreement-architecture.md` |
| 权限 | `frontend-permission-integration-guide.md`, `permission-runtime-governance.md`, `resource-scope-permission-guide.md` |
| 结算 | `multi-flow-architecture-baseline.md` |
| 营销 | `marketing-core-design.md` |
| 消息/通知 | `notification-system-design.md`, `kernel-notify-starter-design.md` |
| 事件/异步 | `domain-event-design.md` |

也检查 `template-scaffold/docs/flow/` 目录下是否有相关的流程图文档。

### Step 3 — 扫描现有代码

根据 PRD 涉及的实体和接口，扫描前后端代码：

**后端扫描（octopus-cloud）：**
- Controller 层：找与 PRD 页面/接口对应的现有 Controller
- Domain 层：找与 PRD 实体对应的 Model、Enum、Repository
- Service 层：找与 PRD 流程对应的 AppService、Action
- Migration：找与 PRD 字段对应的表结构
- DTO：找与 PRD 表单/列表字段对应的 DTO

**存活性验证（关键！）：**
扫描到 Migration 创建的表或代码引用时，必须交叉验证该资源是否仍然存活：
- **表是否被后续 Migration DROP**：搜索 `DROP TABLE IF EXISTS {表名}` 确认表未被删除
- **PO/Mapper 是否存在**：仅有 Migration 创建 SQL 但无对应 PO 类 = 该表可能已废弃或尚未使用
- **Controller/Service 是否有调用方**：检查是否有其他代码引用，避免将死代码当作可复用基础设施
- **前端组件是否在路由中注册**：存在 .vue 文件但未在 router 中注册 = 可能是废弃页面

只有同时满足「Migration 未 DROP」+「有对应 PO/Mapper」+「有 Controller 或 Service 引用」的，才能认定为"现有可用基础设施"。

**前端扫描（octopus-admin）：**
- 页面：找与 PRD 页面路径对应的 Vue 组件
- API 层：找与 PRD 接口对应的 API 函数
- Store：找与 PRD 状态管理相关的 Pinia Store
- 状态展示：看现有页面读的是后端注入的 `{field}Label`（`@DictLabel` 字典）还是前端硬编码 map；新增状态应走字典，方案里写「后端加字典 + 注解」，不要设计前端 code→中文映射

**调用端识别：**同一业务在 PC 后台、BD App、店长 H5 往往是不同的入口接口。扫描 Controller 时区分调用端，PRD 只说「门店能看到 X」时要查清是哪一端的接口，不要只改一端。

**给子代理的调查 prompt** 要写明：以 `origin/dev` 为基线（`git show origin/dev:<path>`），结论附文件路径，引用代码前先做存活性验证。

### Step 4 — 冲突分析与方案决策

对 PRD 中的每个功能点，逐一判定是否与架构冲突：

**无冲突** → 直接纳入技术方案，标注可复用的基础设施

**改造现有接口 / 状态时守向后兼容**：现有接口不换、不删，只追加可选字段或枚举值；已有状态值保留（即使新流程不再产生它）；新分类先对齐现有枚举，不另起一套。需要破坏性变更时作为冲突（类型 A/E）列出并说明影响的调用端。

**有冲突** → 按以下流程处理：
1. **明确说明冲突**：PRD 怎么设计的 vs 架构怎么规定的
2. **分析冲突原因**：产品经理可能不了解的架构约束是什么
3. **给出替代方案**：在满足架构约束的前提下，如何实现产品的业务意图
4. **标注影响范围**：替代方案对 PRD 的哪些部分有影响（页面、流程、字段等）

冲突类型：
- **A - PRD 与架构冲突**：数据模型、状态流转、数据归属、权限设计、组织关系等与架构文档矛盾
- **B - PRD 设计缺陷**：逻辑漏洞、缺失场景、歧义描述、复制粘贴错误
- **C - 架构文档缺陷**：被 PRD 需求暴露出来的架构文档问题（需补充的概念、枚举等）
- **D - PRD 与现有代码不一致**：字段差异、状态差异、接口差异
- **E - 不符合架构理念**：虽不直接矛盾，但违反 DDD 分层、数据库边界、事件驱动等设计原则

### Step 5 — 生成可执行技术文档

将分析结果整合为一份完整的技术实现文档。

## 4. 严重程度

| 级别 | 含义 | 处理要求 |
|------|------|---------|
| **P0** | 阻塞性冲突，不解决无法开发 | 必须在开发前与产品对齐 |
| **P1** | 重要冲突，影响核心功能正确性 | 应在开发前解决 |
| **P2** | 一般问题，不影响主流程 | 可在开发中解决 |

## 5. 注意事项

- **架构不可妥协**：当 PRD 与架构冲突时，技术方案必须遵守架构，由产品调整需求，而不是反过来
- **冲突必须给答案**：不能只说"这里有冲突"就完了，必须给出符合架构的替代方案
- **方案要可执行**：具体到表名、字段、接口路径、组件路径、枚举值，开发人员不需要再做设计决策
- **不遗漏好的设计**：如果 PRD 某些设计优于现有架构，应在冲突决策中注明，建议更新架构文档
- **标注不确定项**：对于拿不准的地方，用 `[待确认]` 标注并说明原因
- **聚焦业务逻辑**：不关注 UI 细节（颜色、间距等），聚焦数据模型、状态流转、权限、接口
- **给出具体位置**：每项都要标明 PRD 章节 + 架构文档/代码文件路径
- **并行扫描**：使用 Agent 工具并行扫描前端、后端和架构文档，提高效率
- **存活性验证**：引用现有代码/表时，必须验证其仍在使用（未被 DROP、有 PO、有引用）
- **基线 origin/dev**：现状结论以 `origin/dev` 为准并在文档中标注 commit；不要拿落后的工作区分支下结论
- **不发明界面元素**：页面详情里的每个按钮、跳转、弹窗、文案、通知、新列都要能指到来源；没来源的进「建议（待产品确认）」附录。为什么：自加的「关联异常」跳转、「结款凭据」曾在评审中被追问来源
- **接口标调用端**：接口表与接口详情都要写 PC / APP / H5，避免只改了一端的入口
- **向后兼容**：现有接口只追加不换不删，已有状态值保留
