# Octopus 产品到开发的同一份规范

产品负责业务逻辑，本 Skill 让生成的原型使用 Octopus 的 Token、组件与页面规范。既能提前参与生成，也能在原型完成后做一次界面规范化；两种入口共用规范。按用户目标工作，不把一次“刷界面”扩大为全系统重构、重建设计系统或强制 Figma 流程。

原型执行入口为 `docs/standards/prototype-authoring.md`；`docs/standards/design-system.md` 保存组件职责目录与设计系统建设状态。先读取适用规则和实际版本；无本地仓库时使用包内规范、Token 与组件基线及来源记录。快照不等于当前定稿，候选稿不自动覆盖现行规范。需要关联 Figma、原型和应用时沿用同一 Markdown 条目，不在各端另立业务口径。

## 来源权威先于原型

按 [已确认分工](references/composition.md#已确认的分工2026-10-29) 执行：LFerp 承载已确认的产品逻辑；已有系统＋设计师稿提供视觉规范；Skill 将业务表达映射到现有 Element／Vab 组件并生成规范原型；Figma 展示组件状态、典型完整页面及本轮实际变化。读取并引用已有业务材料，不重新写一遍 Spec。LFerp 中未经确认的内容、演示数据及历史错误不自动成为标准；来源有冲突时只核对具体受影响项，不用视觉校正擅自改变已确认业务。

视觉规范以 Figma 规范执行版「冷丰ERP·UI规范与组件库」`izYwAFHoZnkV6AxgkhYgyC` 为唯一设计源（2026-11-09 登记，详见 [设计系统源](assets/design-system-source.md)）：Token/组件/页面/图标以该库为准，与 Octopus 规范冲突以其 01 Token 页（`1:86`）裁决，工程现状色差按「工程跟进」处理不改规范；组合教学与详情入口见 [组合与应用](references/composition.md)。

## 现有工程组件先行

需要选择、搭建或校正页面时，读 [组合与应用](references/composition.md)，按订单列表、波次只读详情、波次模板编辑选择对应案例；依据真实参数、插槽、事件和状态组合。用户提供 Figma 组合节点时实际读取对应说明并回到同一 Markdown 和工程入口，不凭组件名称猜用法。无需为了理解一页而读取全部案例。

使用已有 Element / Vab 实现和主题，不再维护第二套原型组件。HTML 原型优先读 [工程组件运行入口](references/runtime.md)：产品可以继续写 HTML，通过已构建资源运行真实组件；页面本身用于展示和验收，不要求另建 Storybook 或先完成全库盘点。当前包携带三个可运行案例及源码摘要，版本快照不自动等于线上最新值。

Markdown 引用组件入口、参数、插槽和已有用例，不重复抄写尺寸或业务逻辑。设计变化先区分页面组合与组件能力；组件缺口回到已有工程修复并构建，不能在单页 CSS 打补丁。历史 `assets/prototype-ui/components.js` 的订单组合仅保留旧原型兼容，不再作为新原型的首选实现。按当前页面需要查目录，订单特有规则不扩成全站规则。

## 选择当前工作

从用户目标判断模式，不反复展示选项。最常用的两个入口都读 [原型生成与界面规范化](references/prototype.md)：

- **生成前调用**：“根据这份业务逻辑，用我们的规范生成原型。”读取逻辑，选择已有 Token/组件/模板，直接输出符合规范的可操作原型。
- **生成后调用**：“把这个已做好的原型，用我们的规范刷一遍。”先读权威设计与已有系统，再检查原型相关状态，确认应保留和应纠正的行为，检查并调整展示和组件用法，输出实际页面、前后差异和逻辑保持的证据。

规范入口是项目 `docs/standards/prototype-authoring.md`（离线用 [规范快照](assets/prototype-authoring.md)）；字段、列、动作和状态是选组件与核对变化的粒度，不要求用户为一次视觉调整重写完整业务 Spec。

- 从现有产品建立/统一规范、Token 或组件库：先读 [实时基础库](references/foundations.md)，完成当前运行环境与代码的对应，再进入页面模式；有同环境、同主题且未失效的基线时复用。
- 按列表/详情职责抽取 atom 和业务组件：读 [组件职责](references/component-roles.md)。
- 一步一步推进、评审定稿或开始下一轮修改：读 [修改循环](references/iteration.md)，沿当前阶段与变更集推进，不每次从头重建。
- 同时生成 LFerp 原型与 Admin 应用：读 [双输出适配](references/targets.md)，使用同一规范条目，分别执行并验收两个目标。
- 安装、换电脑、首次运行或检查工具：读 [环境与迁移](references/setup.md)。
- 写需求、整理 LFerp 原型、建立/更新 Markdown 规格或 Figma 设计：读 [产品流程](references/product.md)。
- 按 Spec 开发、同步修改界面或核对实现差异：读 [开发流程](references/development.md)。
- 验收、比较原型与界面、检查闭环：读 [验收流程](references/acceptance.md)。
- 界面规范检查：读 [界面质量](references/ui-quality.md)，将通用 Web Guidelines 与项目规则一起核对。
- 要求“dogfood / 自己用自己的”：按当前阶段实际执行本 Skill，并用 [实用验证](references/dogfood.md) 记录结果和修订。

不依赖固定页面哈希、列名或布局的专用生成器；直接根据目标原型的真实结构应用规范。业务逻辑调整仍需读取材料、修改相应实现及验收。

每种模式都先读 [来源与交接契约](references/contract.md) 和 [项目规则](references/project.md)。原型阶段沿用可读到的业务材料；只做展示规范化时，Figma、正式交接记录、完整 SDK 对接不是前置条件。仅加载当前阶段需要的其他文件。

## 共同的执行约定

1. 用户只需提供需求或原型/Spec 入口。自己沿导航读相关列表、详情、编辑、配置、明细与页面状态，记录成功读取的范围。材料不可访问时更换适用工具；仍失败则暂停依赖部分，不能用代码或自写方案冒充材料。
2. 把来源事实、用户确认、技术约束、建议/待确认分开。LFerp 的 mock、localStorage、演示账号和示例金额不是真实业务或接口契约。现有代码也可能有错误，不能反过来改需求以迁就实现。
3. 默认以共享 Git 仓库中的 Markdown 规格作为正文，产品、设计和开发读取同一文件及版本；Figma 保留设计节点、样式和指向正文的页面说明。每条业务口径仍追溯已确认材料。建立 Octopus 设计系统时，以用户指定的当前 Octopus 运行界面核验主题/密度与组件，再对应源码和规范；不能从 LFerp 的样式反推 Octopus 基础库，也不能用本地默认值冒充运行值。LFerp 中已确认的页面、流程、字段和交互是产品逻辑材料，沿用并引用原定位；未经确认的内容单列核对，LFerp 的样式不作为视觉规范依据。来源冲突时列出具体条目，暂停受影响部分，不擅自指定某个来源永远覆盖其他来源。
4. 在首次写入前简述目标、已读材料、行为范围、写入对象及完成证据；已有授权内直接推进。新增业务状态、限制、按钮、权限或字段语义必须有来源，建议不自动进入正式 Spec 或代码。
5. 原生 Specs 是用户明确选用且实际可用时的可选载体，不是默认前置条件。Markdown 模式不检查原生 Specs 开通状态；仅使用原生 Specs 时检查 Figma 身份、目标文件归属的 plan 和该 plan 的 specs_enabled。不能用别的 plan 的权限推断目标可用；归属不清才问具体问题。能力被拒绝时停止原生操作，不以其他团队或升级套餐作为默认路线。继续 Markdown 规格与 Design 工作流，明确正文主版本；普通说明面板必须标为“规范说明”，不能冒充原生 Spec，也不能把未执行的同步报成成功。
6. 使用当前环境实际存在的工具。Figma 工具自带的官方技能可用时按操作加载：Specs→figma-spec；画布→figma-use；建文件→figma-create-new-file；页面→figma-generate-design；组件/变量→figma-generate-library；开发→figma-design-to-code；映射→figma-code-connect。能力清单和最低操作约束见 [Figma 操作](references/figma.md)。缺工具或缺官方操作说明时先定位依赖，不猜 API、不把本机缓存绝对路径写进规范。
7. 每个阶段沿用同一任务账本和适用契约。实施前回读本轮实际输入：有 Spec/设计则读相关内容，只有现有原型则读取页面与相关业务行为，不为缺少不相关材料停工。出现变更仅处理相关差异，不能把旧截图或旧导出继续当当前版本。
8. 写后读回实际规范文件与受影响设计节点；只有原生模式才使用原生正文读回。视觉检查另看截图，功能检查另走实际操作与数据回查。单测、mock、合并、部署、运行健康和用户验收分别报告。

## 对用户的输出

先说实际完成了什么，再给 Spec/设计链接、源材料范围、实现/验证证据和具体未决项。说明本次仅同步了哪些对象；读取设计不会自动批准修改设计，代码变化也不自动写回产品规则。同步是显式执行的读取、比较、授权范围内修改与读回，不承诺后台实时双向同步。

环境准备仅交付环境检查报告，不要求生成 Spec/设计交接。Markdown 规格可独立交付，不需要原生 Figma 节点；本地尚未提交发布时标为“本地工作稿、未共享”，不编造远端链接或提交。共享交接以真实可访问的仓库文件及提交定位；不能将本地草稿冒充三方已确认。

有实际可读规格的交接使用 [Spec 结构](assets/spec-template.md) 与 [交接数据模板](assets/handoff-template.json)，按当前授权阶段运行：`python3 <本Skill目录>/scripts/check_handoff.py <交接文件> --stage spec`（只交 Spec）、`--stage design`（Spec＋设计）、`--stage development`（含实现）。不适用项说明原因；不能为通过检查扩展任务或伪造证据。该检查仅检结构和追溯关系，不替代 Figma/业务验收，字段见 [交接格式](references/handoff-format.md)。
