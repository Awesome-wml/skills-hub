# 产品模式

只要求生成原型或将已有原型按规范“刷一次界面”时，优先走 [两个原型入口](prototype.md)，不强制执行下面完整规格与设计交付流程。需要交付开发、规范定稿或同步 Figma 时，再补齐本轮适用项。

先读取 `docs/standards/prototype-authoring.md`（离线为 `assets/prototype-authoring.md`）。产品逻辑不能直接跳成自由绘制的页面：先保留字段/列/动作/状态的稳定 ID，再明确组件、数据绑定、交互结果和适用状态。单列修改检查关联的查询、详情和导出影响；没有来源不自动创建弹窗或新增业务限制。Figma 更新对应设计与同一 Markdown 关联；实际可操作原型和变化清单是交付内容，说明面板不是页面交付的替代品。

1. 根据入口读取 LFerp 页面、相关 PRD/需求、附件及同流程后续页面。记录字段、状态、允许动作、校验、分支和结果，不照搬演示存储/API。页间状态开关只用于观察覆盖，不作为生产能力。
2. 检查当前 Spec、设计库和项目规范。无本地 Octopus 时使用包内有摘要的规范基线；能访问仓库时核验差异。离线基线只能产生绑定该基线版本的草稿/设计，不能声称符合未读到的当前实现。
3. 优先引用 LFerp 已有业务材料与 Spec；Markdown 只补组件映射、本轮差异和缺口。确有本轮新增且已确认的业务内容时，才用 assets/spec-template.md 补对应条目：需求条目有来源；已确认/待确认分开；页面状态与动作矩阵明确；字段与权限不凭架构偏好添加。本地稿与已发布主版本明确区分。Figma 的“规范说明”面板只保留适用条目、设计关联、正文链接及同步版本；正文变更后按差异更新，不维护独立口径。原生 Specs 仅在明确选用且可用时使用。
4. 复用 Figma 已有组件实例与变量。检查它们是否对应 Octopus 组件；搜索命中但属性、来源不对应的组件不能当作已匹配。基础列表/表单/详情优先复用项目套件。记录正常、空、加载、失败、校验、权限/禁用状态各自的来源；原型未出现的通用技术状态单列为候选，不伪称原型已支持或已验收。设计实例显示原型数据时明确标为示例；列表与详情的演示标识或数据冲突需单独记录，不能编造一致的数据。
5. 为每个适用组件记录 Figma 节点、属性/variant/slot、代码组件定位、Token 映射和缺口。没有 Code Connect 时可交付映射清单，但明确“未发布映射”；不得假称 Dev Mode 已连接。创建/发布映射仅在用户授权范围内操作。
6. 设计前与交付前按 [界面质量](ui-quality.md) 核对适用项。回读 Spec 与节点属性，检查关键画面截图及原型导航；按 contract 生成交接。Spec/Design 的具体文件和权限尚未明确时仅暂停相应写入，不要求用户整理章节或重复提供可自行发现的材料。

产品交付应让开发从同一份交接引用找到 LFerp 已确认业务材料、规范化后的原型、适用完整界面状态和本轮变化，而不是只交一张好看的静态截图。项目代码生成器不是这个工作流的产品交付物。
