# 设计修改与定稿循环

Markdown 是共同规范入口；Figma、LFerp、Admin 与规则记录同一条目及版本。Skill 负责执行读取、比较、生成/修改与验读，Markdown 本身不是编译器，也不代表后台实时同步。

## 当前阶段

先读实际源文档、上一份定稿记录和当前变更集。按用户目标选择起点；需要完整流程且授权已足够时连续推进，不在每个阶段重复请求批准。用户要求一步一步时报告当前阶段、已完成证据和下一阶段，不越过尚未解决的依赖。

| 阶段 | 完成对象 |
| --- | --- |
| 基线/职责 | 已读材料、运行版本、列表/详情角色与待核验差异 |
| Token | 当前语义、主题/密度、CSS/Figma 映射及影响 |
| 组件 | atom、业务组合、容器的复用/提取与真实属性、状态 |
| Icon | 角色 ID 对应实际资产、比例、颜色、状态和使用位置 |
| 草稿/生成 | 以同一契约生成 Figma、LFerp/Admin 的受影响草稿，返回实际节点/文件 |
| 评审 | 原需求、视觉、组件、交互、接口和输出差异及真实检查结果 |
| 合并定稿 | 在已有授权内记录明确的定稿决定、最终 Markdown 定位/摘要及关联输出版本 |
| 下次修改 | 从真实定稿基线建立差异，只重走受影响阶段并更新引用 |

在组件阶段先引用 Icon 语义 ID；图形未知时标记，不临时画字符图标冒充最终资产。定稿决定、设计库发布、Git 合并和部署分别记录，不能互相推断；不额外制造团队没有要求的逐人审批流程。实际目标分支、文件和发布权限依当前授权核验。

## 变更集与重复执行

用 [迭代记录模板](../assets/iteration-template.md) 记录本轮。Skill 版本、设计规范版本、组件库版本与应用部署版本分开；没有实际提交/发布就保留本地工作稿，不能把包版本当设计已定稿。

- 输入及依赖未变：复用原产物和仍有效的验收证据，不重复创建组件、页面或新任务。
- 输入变化：比较旧/新条目、Token、组件、Icon 和消费页面；列出要更新、保留、迁移或弃用的对象，再更新受影响文件与节点。
- 有手工改动/WIP：先比对和保留，不用生成结果整文件覆盖。若有生成产物清单，用稳定角色 ID 及实际节点/文件定位进行幂等更新。
- 两端或设计/代码冲突：保留事实与具体差异，暂停依赖该差异的部分，不通过改规范让现有实现自动通过。
- 定稿：读回实际 Markdown 与资产，再更新规则引用及输出的源摘要；旧版/弃用对象保留可追溯关系。没有明确确认不能将 draft/review 标成 final。

既有任务业务 Spec 与设计系统规范可分文件，通过条目 ID 和版本引用；不把所有业务、接口和样式堆进一份无法维护的大文档，也不在多个文件复制同一条规则。
