# 两个入口，同一套原型规范

## 先固定本轮目标

生成前：产品业务逻辑 → 读取 Token/组件/模板规范 → 生成原型 → 验证。

生成后：已有原型 → 对照权威设计与已有系统 → 确认应纠正/应保留 → 更新界面与适用交互 → 对照权威来源验收。

两种方式都由 Skill 指导 Agent 实际执行；Skill 不是自动编译器，也不代表后台同步。产品可以在写逻辑之前、过程中或完成原型之后调用。不要求每次重走“Token 建库 → 组件建库 → Figma → 定稿”的完整建设流程。

## 共用的规范与组件依据

1. 读 `docs/standards/prototype-authoring.md` 和本次页面适用的列表/表格/表单/详情、Token、文案规则；缺仓库时使用包内对应快照，并记录快照版本。已有且未失效的运行 Token/密度证据直接复用，不每次重新盘点全站。
2. 分清真正可复用的实现、原型展示适配与待提取职责。按交互意图选择：导航单号→DocNoLink；复制编号/明文电话→BizNo；日期→VabDateTime；商品/客户/收货/金额/包裹→已有业务展示职责；列表/编辑/详情→已有页面组合。候选名不能冒充已经实现的组件。
3. 读取目标原型项目的真实技术结构。LFerp HTML 原型使用对应的展示适配，不把 Vue 组件名写进 HTML 就算完成，也不把原型 mock 接到生产 SDK。
4. 没有合适组件时记录明确缺口；必要的新展示适配须对应已有规范和业务来源。不能为了看起来变化大，合并业务身份、删列、改状态、改筛选算法或新增按钮。

### 复用现有工程运行资源

HTML 先使用 [工程组件运行入口](runtime.md) 及包内 `assets/prototype-runtime/`。按实际页面选择已验证组件；没有覆盖到的能力从工程已有实现构建扩展，不新写原型版组件，不把独立组件样例或全库建设当成本次交付前置条件。历史 `prototype-ui` 仅兼容旧原型。

### 组件覆盖与还原

生成前选型、生成后清点都从实际页面包含的控件开始，不能只列单号、商品等业务职责而漏掉基础控件。逐项记录「目标节点 → 基线组件/来源 → variant/size/state → 实现 → 验证/缺口」。至少覆盖本页存在的 Checkbox/Radio、Input/Select/日期、Button/Icon、Tag/Label、Table、Pagination、弹层；不存在的组件不强行补入。

- Table 选择列：先核对权威来源的选择范围和交互；原 input 与处理器仅在核验正确时复用；核对未选、选中、半选、禁用、键盘焦点，实际操作单选/全选/取消。只改 `accent-color` 不能证明跨浏览器还原。禁用样式可以在隔离组件样例检查，不得为测试给真实业务行添加禁用规则。
- Tag：确认各字段究竟使用 Tag 还是纯文本，记录尺寸、边框、圆角、浅色背景、文字色和语义映射；只保留原页面的旧 class，或只在映射表写“ATOM-005”，不算已适配。保留业务原值和 Label；原型展示映射不当作 SDK code。
- 用户指定当前运行界面时，实际读取该环境的组件表现。运行值、源码 WIP、泛用规范冲突需逐项登记，不能用本地代码或旧规则覆盖已指定基线。已核验且未失效的证据可复用。
- “业务保持”“基础组件外观/状态”“页面组合”分开验收。列数、文案或动作集合一致，仅证明对应业务内容保持；截图只证明看到的状态。未覆盖的组件和状态列入缺口，不能宣称整页还原完成。

## 入口 A：在生成原型前使用

输入可以是产品的逻辑描述、需求文档或已有业务入口。自行发现相关材料；只追问真正影响行为的缺口。

- 把适用逻辑整理为字段/列/操作/状态的最小契约；沿用已有 ID。不是每次都要求新建一份长 Spec。
- 在生成界面之前选择已有组件、Token、Icon 和页面组合。业务逻辑决定内容与行为，规范决定展示与组件用法。
- 生成实际可操作的原型，检查关键业务分支与适用界面状态。输出原型、采用的规范/组件及具体缺口。

## 入口 B：已有原型生成后使用

先读 LFerp 已确认的页面、流程、字段和交互，沿用原材料及定位；再按已有系统＋设计师稿确定视觉规范与组件组合。Skill 负责语义映射和界面校正，不因样式调整重写业务 Spec 或改变已确认逻辑。旧原型中的未确认内容和来源冲突单列核对，已确认错误不因保留原型而恢复。

- 保存可恢复的原稿及来源摘要，核对 WIP；在已有授权边界内修改，不覆盖他人手工修改。
- 按规范检查 Token、密度、容器、筛选区、工具栏、列展示、业务摘要、操作收纳、Icon 和反馈。只处理适用差异；未变项可以复用证据。
- 对每个实际改动记录“原表现 → 新表现 → 规范条目 → 实际组件/适配定位”。颜色变化、组件复用、交互规范化分别报告；只换 CSS 不能宣称业务组件已抽取。
- 字段、列、事件、筛选/排序/分页、操作条件和金额口径逐项以权威来源核验。可复用的正确部分保留；错误结构和行为按来源纠正，不要求原列数或旧处理器不变。不能自行补未被来源支持的业务。
- 实际打开生成稿验证受影响行为；对照权威设计与系统验证，并用原稿说明前后变化；“与原稿一致”不是正确性标准。截图证明外观，操作证明交互，源码或输出摘要用于证明保留范围，各自记录。

## 本次完成的边界

界面规范化的交付是：实际原型、规范/组件采用记录、前后变化、逻辑保持检查和未完成项。没有视觉差异时可以明确“已符合，本次无改动”；不能为制造差异而扩大设计。

Figma、规范定稿、开发交接按用户当前目标追加；Figma 不可用不阻断本地原型生成或展示规范化。开发交付时再携带同版 Markdown、原型、适用 Figma 节点、差异及真实 SDK 映射。没有生成 Admin 代码就明确未实现。

声称 dogfood 前，必须用此模式在真实目标上执行并保留上述结果；只更新 Skill、跑预检/格式校验或输出说明页，不算实用验证。

## 跨模块来源

先查项目 `docs/standards/component-catalog.md`，无 checkout 时读 `../assets/component-catalog.md`。BASE 是基础控件，ATOM 是语义展示，PATTERN 是通用组合，BIZ 是业务职责。运行已见、代码已读、Figma 已建、交互已验分别记录；订单样本不代表全库。具体状态、来源和适用差异以目录为准。
