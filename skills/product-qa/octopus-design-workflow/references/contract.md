# 来源与交接契约

## 权威来源

按 [已确认分工](composition.md#已确认的分工2026-10-29) 工作：LFerp 提供已确认产品逻辑，读取并引用已有材料，不重新写业务 Spec；已有系统＋设计师稿提供视觉规范；Skill 映射现有组件；Figma 展示规范和实际变化。旧原型中的错误、未经确认的内容和演示数据仍须区分；不从历史错误恢复“22 列不变”等失效验收条件。

## 从同一个入口工作

生成前的最小入口是产品业务逻辑或需求入口；生成后的入口是 LFerp 原型、其中已确认的业务材料，以及适用的视觉规范来源。Skill 自行读取适用的共同规范和相关页面状态。有业务 Spec/Figma 设计时读取受影响内容；单次界面规范化不以额外补齐共享 Spec、Figma 或 SDK 为前置条件。未提交发布就明确本地产物未共享，不捏造远端位置。默认不创建原生 Spec，不要求 fileKey/nodeId；明确选择原生模式且可用时才使用原生文档。只影响依赖步骤的缺口才提问。

原型阶段记录权威来源、所用规范/组件版本、核验后应保留或纠正的业务行为、实际变化、产物和检查结果。下面的完整交接字段用于正式规格/设计/开发交付，不能反过来阻止范围明确的本地原型规范化。

一次交接同时包含：任务范围、LFerp 已读页面/状态和内容摘要、需求条目、规格的载体、仓库/相对路径/提交和正文 SHA256（原生模式另记录文件/文档根节点）、设计节点及样式证据、组件映射、接口来源、决策、验收条目。日期用实际读取时间。正文摘要对实际读到的 Markdown 原始字节计算（原生模式对 getContent 返回的 Markdown UTF-8 计算），不自行声称是 Figma 原生 revision 字段。设计无可验证 revision 时记录读取时间、返回节点属性/变量绑定摘要与截图证据，不编造版本号。

共享 Spec 和交接只使用同事能访问的 URL 或仓库相对定位＋提交，不放本机绝对路径、localhost、临时鉴权下载链接、账号令牌或客户原始数据。机器路径属于本地环境配置，不进入共享交接。

## 追溯粒度

每个功能/字段约束/状态动作有稳定条目 ID；每个 ID 记录来源 URL、章节或页面状态、确认性质、Spec 位置、关联 frame、组件/Token、实现定位与验收。已有 ID 继续使用，不强制改号。

最小链路：LFerp 已确认条目（已有 Spec 直接引用）→ 适用规范与本轮差异 → 设计节点/状态 → 代码组件/接口 → 验收预期与证据；没有新业务内容不另写 Spec。某项无实现或设计时写清不适用原因。禁止仅写“按原型”“已同步”“与设计一致”。

实际接口是字段名、类型、空值与提交语义的来源；契约缺字段就报具体缺口。仅缺技术字段时不能推导新业务限制。已有 Label 字段用于展示；编辑保留 value/code。

## 差异处理

- LFerp 本地与发布站不同：记录两者定位/摘要，回读需求实际链接；不能把本地旧页直接作为整改目标。
- LFerp、需求、Spec 或画面冲突：指出具体规则及各来源内容，保留未冲突部分，问题定到影响结果的口径。
- Spec 更新：先读取并比较，再更新受影响映射和验收；保留稳定 ID 和评论锚点。开发未经授权不改产品规则或设计以让代码“通过”。
- 样式与 Octopus Token 冲突：先寻找现有主题/属性/变量映射；无法表达时提出具体差异与必要扩展，不静默硬编码或整体换库。
- 本地实现含 WIP：逐项标记材料支持/必要技术约束/缺少来源；保留用户工作，不自动打包、提交、合并或部署。

确认状态来自用户或有记录的评审，不能从“没回复”或 agent 自己写了 Spec 推断已确认。验收结果保留 passed/failed/not-run/blocked 的真实证据；不把生成成功或自动测试通过转成业务验收通过。

JSON 字段及验证边界见 [交接格式](handoff-format.md)。
