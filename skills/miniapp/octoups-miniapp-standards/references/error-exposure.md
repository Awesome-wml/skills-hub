# 错误暴露原则（禁止前端吞掉问题）

只在任务确实涉及接口错误、字段兜底、`catch` 处理、空态/错误态切换、图片或文件
资源失败时再读这份 reference。

## 强制原则

- 前端不得以任何方式掩盖、消化或静默处理问题，真实失败必须沿失败路径暴露。
- 后端业务错误、字段缺失、契约不成立、资源坏链，默认都按“问题本身”处理，不要
  包装成“虽然成功但暂时没数据”。
- 可以做 UI 收尾，但不能把失败改成成功。

## 禁止写法

| 禁止写法 | 为什么不行 | 正确方向 |
| --- | --- | --- |
| `catch {}`、`catch (err) { console.log(err) }`、Toast 后直接结束 | 错误被静默吞掉，调用方和用户都看不到真实失败 | 做完收尾后继续 `throw` / `return Promise.reject(error)`，并让页面进入真实错误态 |
| `await api().catch(() => [])`、`catch(() => null)`、`catch(() => ({ }))` | 失败被伪装成成功返回，后续链路失真 | 保留 rejected promise 或显式失败分支 |
| `res.total ?? 0`、`list || []`、`title ?? ''`、`enabled || false` | `null` / `undefined` 被静默改造成业务值，根因被抹平 | 保持原值暴露，在错误态、方案、plan 或台账里记录契约问题 |
| 后端异常字段由前端补默认值兜底 | 掩盖后端数据问题，联调时无法定位根因 | 按后端契约问题记录，必要时提示用户操作失败 |
| 字段缺失时前端自行推断、补算或拼装 | 计算值不可信，且会制造“看起来没问题”的假象 | 只展示后端真实给出的值，不擅自推断 |
| 图片 / 文件 URL 失败后自动切默认图、默认封面、备链 URL | 坏链被掩盖，资源问题无法暴露 | 保持失败可见，并记录为后端资源问题 |
| 请求失败后直接切成空态 | 把错误态伪装成正常空数据态 | 空态只用于“成功但为空”，失败必须走 error |

## 允许的处理方式

- 可以在 `catch` / `finally` 里关闭 loading、解锁按钮、回滚乐观 UI。
- 用户可见操作失败时，应给出明确失败提示；如果后端已返回 `message`、`code`、
  `traceId`，优先保留原语义，不要统一改成泛化文案。
- 如果问题来自后端契约或资源，默认写入 `docs/*.md`、`dev-plan/*.md` 或实施台账，
  不要只在代码里“兼容一下”。
- 只有在用户明确接受临时兼容时，才允许做最小范围、可追踪、带风险说明的过渡处理。

## 快速检查

提交前至少自问这 4 件事：

1. 这里的 `catch` 是不是只做了清理，却把失败悄悄改成了成功返回？
2. 这里的 `??` / `||` 是在做展示默认态，还是在掩盖后端坏数据？
3. 这里的空态是不是其实应该是错误态？
4. 这里的默认图 / 默认文案 / 默认数值，是不是把资源或契约问题藏起来了？
