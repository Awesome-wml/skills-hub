# SDK runtime 与集成边界

这份 reference 只在任务确实碰到 `sdk` / `OpenAPI` / `orval` 时再读，不要默认整份塞进上下文。

## 一眼判断改哪里

| 任务现象 | 优先改动位置 |
| --- | --- |
| 页面要接真接口，但已有 `services/*.ts` | `miniprogram/services/*.ts` |
| DTO 字段、query/body、返回值类型不对 | `openapi/*.json` 或后端契约 |
| SDK 生成函数命名 / 分文件方式不对 | `scripts/gen-sdk.mjs`、`orval.config.cjs` |
| SDK 请求 baseURL / header / 错误处理不对 | `miniprogram/sdk/mutator.ts`、`miniprogram/sdk/runtime.ts` |
| 生成后目录内容丢失 | 先确认是不是误把手写逻辑放进了生成目录 |

## 当前 repo 的两套请求链路

### 1. 现有主链路：`miniprogram/utils/request.ts`

- 支持 `system / commerce / marketing / bff` 四类 baseURL
- 从 `miniprogram/config/env.ts` 解析 host
- 会把 `R<T>` 解包成 `data`
- 会触发统一的登录失效清理和事件派发
- 当前大多数 `miniprogram/services/*.ts` 都走这条链路

### 2. SDK 链路：`miniprogram/sdk/mutator.ts`

- 由 orval 生成函数调用
- 返回整包 `R<T>`，不是直接返回 `data`
- 通过 `miniprogram/sdk/runtime.ts` 注入鉴权 header、解析 host、处理登录态清理
- 默认把后端错误继续 `reject` / `throw`，不在 runtime 层统一 Toast 或兜底成空数据
- 未显式传 `baseURL` 时，会按 path 前缀推断 host，不依赖 `app.globalData.baseUrl`

这两条链路目前不是同一个抽象层，不能假设“把 service 改成 SDK 调用”就一定是无损替换。

## 接入 SDK 时的推荐边界

优先顺序：

1. 页面 / 组件继续只认业务 service
2. service 内部决定是走 `request.ts` 还是生成 SDK
3. 如果走 SDK，在 service 内把 `R<T>` 收敛成页面真正需要的返回结构，但不要把
   后端错误偷偷改写成成功结果
4. DTO 原名尽量保留在 service 边界以内，展示层再做最小映射

不推荐：

- 在页面 `.ts` 里直接 import `miniprogram/sdk/*`
- 在生成目录里夹带业务逻辑
- `catch(() => null)`、`catch(() => [])`、Toast 后吞错、默认空对象这类静默兜底
- 为了过类型把 `number` / `string` 来回强转一层又一层

## 错误边界原则

- `request.ts` 和 `sdk/runtime.ts` 默认只负责传输层错误透传，以及登录态清理这类
  必要副作用；不要把它们做成“统一兜底器”
- service / page 如果只是为了收起 loading、恢复按钮状态、回滚乐观更新，可以在
  `catch` / `finally` 做 UI 收尾，但不要把失败改成成功返回
- 后端明确返回了 `message`、`code`、`traceId` 时，优先保留原语义，避免再包一层
  泛化文案把真实问题抹平
- 后端字段值如果违反契约，例如该有值却给 `null` / `undefined`，不要用
  `?? ''`、`|| []`、`|| {}`、默认数值或默认布尔值把它修平
- 后端图片 URL 如果加载失败，不要在页面 `binderror` 或 adapter 层切默认图；
  这类错误应直接暴露并记录为后端资源问题

### 禁写法速查

| 禁止写法 | 为什么不行 |
| --- | --- |
| `catch(() => [])` / `catch(() => null)` | 把 rejected promise 伪装成成功结果 |
| `catch(err => { console.log(err); return; })` | 调用方失去失败信号，只剩控制台日志 |
| `res.xxx ?? ''`、`res.list || []`、`avatar || DEFAULT_AVATAR` | 用展示值掩盖了真实坏数据 |
| 请求失败后直接展示空态 | 错误态被降级成“成功但为空” |

需要更完整的规则时，再读
`../../octoups-miniapp-standards/references/error-exposure.md`。

## 重生成前后检查清单

重生成前先确认：

- 改动应该落在生成脚本 / mutator / 契约，而不是生成目录
- 本次是否真的需要拉远端 spec，还是离线重生成就够
- 是否会影响 `openapi/*.json` 的缓存文件

重生成后至少检查：

- 目标 endpoint 是否出现 / 消失
- 目标 model 字段类型有没有变化
- `mutator.ts` 是否仍是手写文件，未被覆盖
- 业务 service 是否还和新生成签名对得上

## Long id 问题

如果 SDK 里出现：

- DTO 的 `id` / `storeId` / `channelSkuId` 等本应是雪花 long 的字段被生成为
  `number`

处理顺序：

1. 先确认是不是 OpenAPI 契约就这么暴露出来的
2. 不要直接 `as string`
3. 在方案 / plan / 对接台账里记录“后端需补 `@JsonFormat(shape = STRING)`”
4. 只有用户明确接受临时兼容时，才在业务边界做最小范围的兜底转换，并说明风险
