# Webapp Testing E2E 测试

## 什么时候用

以下请求直接使用本 skill：

- “帮我给这个网页写 E2E 测试”
- “做个自动化测试用例”
- “做 E2E 测试 / 端到端测试”
- “用浏览器验证这个页面 / 流程”
- “跑一遍新增、编辑、删除、查询流程”
- “检查页面有没有报错、接口有没有异常”
- “验证弹窗、抽屉、表单、表格、路由跳转”
- “改完后帮我联调一下”

如果测试目标是 Web 页面或后台管理系统，并且需要真实浏览器证据，就走本 skill。

## 安装命令

如需安装此 skill，可使用：

```bash
npx skills add webapp-testing -y -g
```

## 核心能力

- 基于 Playwright 生成 E2E 测试用例。
- 自动化页面导航、表单填写、点击、选择、提交和断言。
- 记录截图、控制台日志、网络请求和失败现场。
- 生成测试报告，说明通过项、失败项、阻塞点和未覆盖范围。
- 结合真实浏览器实测结果调整测试选择器和等待策略，让用例可直接运行。

## 核心原则

- 先明确验收目标：页面地址、用户路径、测试账号、期望结果、是否允许写入或删除数据。
- 开始前检查是否已有本地服务运行；不要重复启动 dev server。
- 浏览器操作前先列出标签页，再获取快照；每次会改变页面结构或 URL 的操作后重新获取快照。
- 优先使用可访问性快照里的元素 ref 操作；坐标点击只在没有稳定 ref 时使用，且必须使用刚截取的截图坐标。
- 发现登录、验证码、权限不足、危险确认、缺少测试数据等阻塞时停止并报告，不要硬猜。
- E2E 验收要同时关注页面结果、控制台错误、关键网络请求和可见文案。
- 生成 Playwright 用例时优先使用用户可见的 role、label、placeholder、text 定位；避免脆弱的深层 CSS 选择器。
- **样式 / 布局类改动不以「代码看起来对」结案**：编译后 CSS 正确不代表浏览器渲染正确。要在真实浏览器里看到结果（截图 + 关键元素实际尺寸）；自己无法实测时，结论只能写「已改，请你验证」，并给出本地 `pnpm dev` 的 localhost 访问路径让用户实测，用户确认后才算修好。为什么：2026-10 一次 flex 挤压问题只加了 `min-width: 0` 就宣称修好，用户实测并没好。

## 标准流程

1. 准备测试上下文
   - 确认测试范围和成功标准。
   - 检查运行中的终端，确认应用 URL。
   - 如需启动服务，先确认父目录和 package script，再启动。

2. 打开浏览器并锁定会话
   - 先用 `browser_tabs` 查看现有标签页。
   - 已有目标标签页时先 `browser_lock`。
   - 没有标签页时先 `browser_navigate` 到目标 URL，再 `browser_lock`。

3. 建立页面基线
   - 使用 `browser_snapshot` 获取页面结构。
   - 必要时使用 `browser_take_screenshot` 做视觉基线。
   - 检查是否已登录、路由是否正确、基础数据是否加载完成。

4. 执行业务路径
   - 每次只做一个明确操作，然后用快照或请求结果验证。
   - 表单测试覆盖必填校验、正常提交、编辑回显、取消/关闭行为。
   - 列表测试覆盖查询、重置、分页、状态筛选、操作列按钮。
   - 删除、停用、提交等会改变数据的操作，必须确认用户允许后再执行。

5. 生成或完善 Playwright 用例
   - 将实测路径沉淀为 `test` 用例，包含导航、操作、断言和必要的等待。
   - 使用 `test.step` 拆分页面路径，失败时便于定位。
   - 对关键状态使用可见文案、URL、表格数据、接口响应或 toast 做断言。
   - 对不稳定加载使用明确等待条件，不使用固定长时间等待。

6. 检查运行证据
   - 布局问题（元素被挤没、宽度为 0、溢出）用 `getBoundingClientRect()` / `boundingBox()` 读出实际宽高作证据，并在不同视口宽度下各看一次；只看截图容易漏掉被挤到很窄的元素。
   - 查看控制台错误与警告，区分历史噪声和本次新增问题。
   - 查看关键接口请求状态、参数和响应摘要。
   - 截图只用于视觉确认；最终结论必须以可见状态或接口结果支撑。

7. 收尾报告
   - 说明通过的路径、失败的断言、阻塞点和剩余风险。
   - 列出未执行的测试项及原因。
   - 完成后释放浏览器锁。

## 浏览器工具约束

- 使用 MCP 浏览器工具前，先阅读对应工具 descriptor；遵守 cursor-ide-browser 的锁定、快照和等待策略。
- 页面结构变化后不要复用旧 ref；重新 `browser_snapshot` 后再操作。
- 等待加载时使用 1-3 秒短等待加快照检查，不做长时间盲等。
- 同一失败操作不要重复超过 1 次；需要新证据后再尝试。
- 如果 4 次尝试仍无进展，停止并报告当前页面、目标、阻塞和建议下一步。

## Playwright 用例约定

- 测试文件优先放在项目已有 E2E 目录；没有约定时，先检查 `tests/`、`e2e/`、`playwright.config.*`。
- 不把真实账号、密码、token 写入测试代码；使用环境变量或项目已有登录 helper。
- 对新增、编辑、删除类测试使用专用测试数据命名，便于清理。
- 若操作会写入真实业务数据，先向用户确认是否允许执行。
- 用例应能独立运行，不依赖上一个测试残留的页面状态。
- 生成测试后优先运行目标用例；无法运行时说明原因和手动验证结果。

## 验收清单

- 页面能打开且路由正确。
- 状态、枚举列显示的是中文文案（后端注入的 `{field}Label`），没有裸露英文 code。
- 关键首屏内容、标题、按钮和表格列符合预期。
- 搜索、重置、分页或筛选能触发正确数据变化。
- 表单必填校验、输入校验、提交成功和错误提示符合文案规范。
- 新增或编辑后列表刷新，回显数据正确。
- 控制台没有本次引入的错误。
- 关键接口没有异常状态码，参数和响应字段与页面行为一致。
- 测试过程没有留下不应存在的脏数据；如留下测试数据，需要说明。
- Playwright 用例可读、选择器稳定，并包含关键断言。
- 测试报告能说明通过、失败、阻塞和未覆盖内容。
- 可视化改动：有真实浏览器截图 / 尺寸证据，或已明确交给用户在 localhost 实测；用户确认前不写「已修复」。

## 报告格式

简洁报告即可：

```markdown
E2E 验收结果：通过 / 未通过 / 部分通过 / 待用户实测（可视化改动未经真实浏览器确认时用这一档）

已验证：
- 路径 A：结果
- 路径 B：结果

发现问题：
- 问题描述，复现位置，影响范围

未覆盖：
- 未测试项及原因

证据：
- 页面状态、关键请求、控制台结果或截图说明
```
